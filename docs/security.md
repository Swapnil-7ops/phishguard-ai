# PhishGuard AI — Security Architecture & Hardening Guide

## 1. Overview & Threat Model

PhishGuard AI is an academic cybersecurity platform for multi-modal phishing detection. Because the system accepts potentially hostile inputs from untrusted sources (malicious URLs, phishing text messages, weaponized QR codes, deceptive login screenshots, and adversarial `.eml` email files), defensive hardening and containment are foundational architectural requirements.

The application adheres to the principle of **passive, zero-execution static analysis**: under no circumstances will PhishGuard AI connect to, download from, or execute content provided in user submissions.

---

## 2. Multi-Modal Security Controls

### 2.1 URL Analysis (Mode A)
- **Zero Remote HTTP Requests:** PhishGuard AI does **not** fetch destination web pages, follow HTTP redirects, or download remote assets. Analysis is strictly lexical and structural using 25 deterministic features.
- **SSRF (Server-Side Request Forgery) Immunity:** By prohibiting socket connections to user-submitted hosts, internal network scanning, cloud metadata theft (`http://169.254.169.254`), and localhost probes are impossible.
- **Dangerous Scheme Interception:** Schemes such as `javascript:`, `data:`, `file:`, `vbscript:`, and `blob:` are detected and rejected prior to model inference.

### 2.2 Message & SMS Analysis (Mode B)
- **Length & Payload Bounding:** Raw text input is bounded to 10,000 characters to prevent ReDoS (Regular Expression Denial of Service) and buffer exhaustion.
- **Cascaded Link Isolation:** Embedded URLs extracted from messages are analyzed statically through the URL analyzer with zero network dereferencing.

### 2.3 QR Code Quishing Detection (Mode C)
- **Safe Raster Decoding:** Image decompression is performed in memory via Pillow and OpenCV.
- **Immediate Scheme Filtering:** Decoded payloads are examined for non-HTTP schemes (`javascript:`, `data:`, `file:`) and blocked immediately with a maximum risk score of 100 before any URL feature extraction occurs.
- **No Browser / Shell Spawning:** The decoded destination URL is never launched in a browser subprocess.

### 2.4 Screenshot / Visual Phishing Detection (Mode D)
- **In-Memory Image Processing:** Images are decoded directly into RAM (`io.BytesIO`) and discarded immediately upon feature extraction.
- **Upload Size & Type Limits:** File sizes are strictly capped at 10 MB, and extensions are validated against an allowlist (`.png`, `.jpg`, `.jpeg`, `.webp`, `.bmp`).
- **No Remote Screenshot Crawling:** PhishGuard does not use headless browsers (Puppeteer, Selenium, Playwright) to capture remote websites, eliminating server-side browser exploitation vectors.

## 3. Phase 13 Email (.EML) Analysis Security Hardening

Email files represent a complex, adversarial multi-part attack surface. PhishGuard AI enforces the following strict security controls:

### 3.1 Zero Attachment Execution & Unpacking
- **Metadata Inspection Only:** PhishGuard AI extracts filename, MIME content-type, file extension, and byte size.
- **No Binary Import / Dynamic Execution:** Attachment payloads are never imported, executed, or unpacked.
- **Double Extension Detection:** Files attempting to disguise executables behind benign extensions (e.g. `invoice.pdf.exe`) are flagged as critical threats.
- **Path Traversal Defense:** Filenames containing path traversal sequences (`../`, `..\`) are sanitized and flagged.

### 3.2 Safe HTML Email Parsing & XSS Prevention
- **Standard Library Parser:** HTML bodies are parsed using Python's `html.parser.HTMLParser` to extract visible text chunks and hyperlink targets.
- **Script & Iframe Neutralization:** Active tags (`<script>`, `<iframe>`) are identified, flagged as security anomalies, and their text contents are excluded from visible text extraction.
- **Link Scheme Validation:** Hyperlink destinations beginning with `javascript:` or `data:` are flagged and excluded from the extracted HTTP URL list.
- **Event Handler Stripping:** Attributes beginning with `on` (e.g. `onclick`, `onload`, `onerror`) are flagged as malicious code injection.
- **No Raw DOM Injection:** The frontend UI uses standard text nodes and HTML entity escaping (`escapeHtml()`) before rendering email subject, headers, or body text into the browser.

### 3.3 Passive Authentication Verification
- **Header-Only Evidence:** SPF, DKIM, and DMARC statuses are extracted strictly from the `Authentication-Results` header generated by the receiving MTA.
- **Zero External DNS Lookups:** The system does not issue outbound DNS queries, preventing DNS amplification, rate-limiting exposure, and network information disclosure.

## 4. Threat Intelligence Data Minimization

PhishGuard AI integrates with VirusTotal v3 for optional threat intelligence corroboration, subject to strict data minimization policies:

| Data Type | Sent to VirusTotal? | Rationale |
|---|---|---|
| Extracted Destination URLs | **YES** (if TI configured) | Permissible reputation check on web URLs. |
| User Email Addresses | **NO** | Strictly retained in memory; never transmitted. |
| Email Subject Headers | **NO** | May contain proprietary or sensitive business context. |
| Email Body (Text/HTML) | **NO** | May contain confidential employee or financial text. |
| Attachment Payloads/Hashes | **NO** | May contain proprietary corporate documents. |
| User IP / Session Metadata | **NO** | Privacy protection by design. |

---

## 5. Secret Management & Credential Protection

- **Environment-Driven Secrets:** All API keys (`VIRUSTOTAL_API_KEY`, `FLASK_SECRET_KEY`) are loaded via environment variables or a local `.env` file that is excluded from version control (`.gitignore`).
- **Response Redaction:** API response payloads and database records are scrubbed to ensure API keys are never exposed in user-facing JSON.
- **Credential Sanitization in Logs:** Passwords, bearer tokens, OTPs, and credit card numbers embedded in URLs or messages are redacted (`[REDACTED]`) before database insertion.
